# 정동적·터널 인지 변경 및 신호등 분석

## 적용 내용

- M3와 M8 모두 경로 좌우 8m를 관측·추적한다. 기존 4m 수집/6m 예측
  불일치를 해소했다. 정지 트리거 폭은 확장하지 않았다.
- `/motion_tracking/dynamic_risk`를 두 구간에서 공유한다. 1.2m/s 미만의
  느린 횡단도 스캔 시각 자세로 보상한 위치 회귀가 일관적이면 예측한다.
  속도 미확정 상태에서도 이 관측 근거를 사용할 수 있고, 관측이 오래됐거나
  접근 방향이 반대면 이 경로로 제동하지 않는다.
- `obstacle_perception_node/mission_filter_profiles`의 static/dynamic/tunnel은
  지면 제거 이후 ROI·클러스터·형상 필터만 바꾼다. GroundGrid는 공유한다.
  기존 고주로 TTC 전용 설정은 별도로 유지한다.
- 터널은 8cm 복셀로 밀집 점군을 줄이고, 긴 종방향 측면 구조물은 실제
  횡방향 점유 폭으로 검사한다. 일반 객체 추적에서 분리한 구조물도 0.5m
  셀별 충돌 기하로 회피 노드에 전달한다. 횡방향 차단물은 이 분리에
  해당하지 않는다. 이는 기하 기반 후보 분리이며 의미론적 벽 확정은 아니다.
- Apollo 측정 후보를 최대 3개 시간 간격에서 교차 확인한다. 시간 간격 간
  불일치는 공분산에 더하고, 상관 관측 수로 나눠 신뢰도를 부풀리지 않는다.
  동적·고주로가 같은 구현을 사용한다. 속도 방향 불확실성을 계산하며,
  거의 정지한 객체에는 방향을 확정하지 않는다.
- 정적 확정에는 추가 관측 시간이 필요하다. 최근 움직였던 객체는 2초간
  동적 이력을 유지한다. M8의 미확정/동적 전방 물체는 회피 진입을 막는다.
- `mission_mode=tunnel`과 csv=3을 함께 확인해 M8을 고주로 제어 제외
  조건에서 분리했다. M8 구간 상태 메시지 상실 시 인지를 유지한다.
- M8 대향차량/미확정 측면 객체의 ID를 보관한다. 단순 소실로 통과 처리하지
  않고 뒤쪽 관측 또는 정적 확정으로 해제한다. 경로 탐색 실패 시 M8에서는
  이전 회피 경로를 재사용하지 않고 정지 요청한다.

## 오픈소스

기존에 포함된 Apollo `measurement_collection.cc/.h`를 그대로 사용했다.
원본 커밋: `d53aa3da47a06a08e6d0cd175d5623a34fa0d6aa`.
라이선스·해시는 `apollo_motion_bridge/vendor/UPSTREAM.json`에 있다.
이는 Apollo 전체 추적기를 가져온 것이 아니다. 데이터 연관, 시간 후보 선택,
분류 및 미션 제어는 이 프로젝트의 구현이다.

## 검증

`source devel/setup.bash` 후:

```bash
python3 -m unittest discover -s src/apollo_motion_bridge/test -p 'test_*.py'
catkin_make --pkg apollo_motion_bridge new_lane -j4 -l4
```

34개 테스트: 양방향 횡단, 느린 횡단, 이탈 방향, 오래된 관측,
정지 물체, 터널 측면 벽/횡방향 차단물, 고속 직진·횡방향 속도,
감속 추종, 부분 가림, 시간 역전, 공분산·방향 불확실성.
빌드 및 설정 검증 통과. 이는 합성 입력/콜백 검증이며 실제 대회 주행의
속도·방향 오차 개선율이나 처리 지연 상한을 입증한 결과는 아니다.

## 현장 검증이 필요한 조건

- M8 범위는 현재 section_router의 기존 추정값을 사용한다. 정확한 터널
  시작·끝 및 GPS 음영에서의 경로/차선 추종 품질은 아직 검증하지 않았다.
- 구조물과 붙은 보행자의 점군 분리, 곡선 터널 벽, 부분 가림 시 ID 변경을
  실제 점군으로 검증해야 한다. 긴 선형 차량 측면도 구조물 후보가 될 수
  있으므로 collision geometry를 제거하면 안 된다.
- 대향차량 ID 소실 시 정지가 오래 유지될 수 있다. 공간적 통과 확인과
  ID 재연결, 회피 시작~완전 복귀까지의 곡선 시간 점유 예측은 추가 작업이다.
  현재 대향차량 제한을 완성된 대향차로 진입 허가기로 해석하면 안 된다.
- GPS 복귀 좌표 점프를 포함한 추적 정확도, LiDAR/odom 시간 오차, 시야에
  따른 속도 상한은 기록 데이터 및 시뮬레이터에서 확인해야 한다.

## 신호등 — 분석만 수행, 관련 코드 미변경

현재 그대로는 Autoware EKF와 결합한 신호등 미션 수행을 보장할 수 없다.

1. competition.launch는 EKF 모드에서 map_localizer를 기본으로 끈다.
2. EKF는 전체 UTM, MGeo는 원점 `(302595, 4124145)`를 뺀 로컬 좌표다.
   map_localizer의 odom_cb는 원점을 빼지 않고 입력 위치를 직접 대입한다.
   동일 지도 지점으로 비교: 로컬 좌표 매칭 0m, UTM 직접 매칭 약
   4,135,226m. 단순 `use_odom:=true` 추가 실행 안내는 올바르지 않았다.
   좌표 변환뿐 아니라 공개 pose/marker의 frame_id와 TF 정합도 필요하다.
3. 신호등 제약의 csv=0, [1800,4600]/[5400,6200] 게이트는 존재한다.
   다만 입력 freshness만 검사하며 section_router의 index_valid는 검사하지
   않는다. 예측 인덱스도 허용되는 동작이다.
4. front_axle_offset_m=3.845는 축거+전방 오버행이다. 앞바퀴 위치와 같지
   않으며 실제 base_link/GPS 기준점을 먼저 확인해야 정지 마진을 검증할 수 있다.
5. localizer는 신호 미상이고 정지선 50m 안일 때 정지를 요청한다. 모델 실패가
   대기로 이어질 수 있다. 모델 파일 존재는 확인했으나 인식 성공률은 미검증이다.
6. detector의 always_infer=false: 노드는 살아 있어도 전방 정지선이 없으면
   추론을 쉬므로 '전 구간 항상 추론'이라고 표현하는 것은 정확하지 않다.
7. 제약 해제 후 직접 속도캡을 발행하지 않는 구조여서 MPC의 마지막 캡은
   기본 0.5초 timeout까지 남을 수 있다. 구간 밖 즉시 제동 해제를 보장하는
   것과 신호등 제약 active=false는 구분해야 한다.

관련 신호등 코드, 런치, 미션 범위는 이번 작업에서 수정하지 않았다.
